How wanting my own Spotify turned into all of this

It started as a way to stream my own music instead of Spotify, and keeping it the way I wanted kept adding pieces until it was a home server with a job queue and a few machines doing the work behind it.

It started with wanting my own Spotify

I left Spotify because I didn't like how much their algorithm steered what I listened to, and I missed curating my own library. So I set up Navidrome on a home server to stream my own music, and having my own copy of everything was good for about a week before I started missing two things, the playlists and the lyrics. Going after those two is what built everything else on this site.

Lyrics came first. A cron script fetched synced lyrics from LRCLIB, an open-source lyric library that keeps growing, and wrote .lrc sidecars into the library so the players would scroll them. I run it on a nightly timer for two reasons: so any new music I add gets its lyrics on its own, and because LRCLIB keeps growing, so a track that had nothing last time might have lyrics the next time it runs. It also has polite rate limiting and a cache for the misses. For the tracks nobody had ever transcribed, I eventually pointed stem separation and Whisper at my own files, and I added romaji and translation for the Japanese half of my collection. The playlists turned into mood analysis, which is a Navidrome plugin with an audio-ML sidecar that scores every track and feeds 48 generated mood playlists, and later a chat harness that builds a playlist for whatever mood I ask for and answers music trivia from real sources instead of from a model's imagination.

The mood playlists then led to the pictures, because I wanted to create covers for the playlists, but the good image models needed to run on my stronger machine. That forced the first real architecture decision, and everything since has inherited it, which is that the GPU machine pulls jobs, and the server never reaches into it. The worker polls a queue, renders, and sends the results back, and because different models finish at very different speeds, each one shows up as soon as it is done rather than waiting on the slowest.

The day a second machine started polling the first, the hobby had turned into a distributed system.

The pattern gets copied over and over

Once a pull-queue existed, every new thing I wanted became another lane on it. Voice cloning went on for a daily listening brief, and stem separation went on and promptly fed back into the original lane by transcribing lyrics LRCLIB didn't have, which is where one of the commit messages from that stretch came from, "don't pay demucs to prove a track has no vocals." Looping canvas videos for album art went on after I probed the official source and hit a wall, and then came image-to-3D meshes and a local coding agent, which I added because building my chat assistants on a small local model had already shown me that models tuned for a consumer graphics card can carry real work, and I didn't want every task leaning on paid frontier tokens. Each lane copied the same queue-and-lease mechanics, and the workers advertise what they can do through a capability heartbeat that probes everything live at beat time, a rule I wrote after a stale venv spent four days advertising a capability it didn't actually have.

At the busiest stretch it was two machines and several AI coding agents coordinating through a shared board, along with a knowledge-base wiki where I wrote things down so I wouldn't have to work them out a second time.

One GPU shared by many stacks

A single 12 GB consumer card serves image generation, stem separation, several local LLMs, and a coding agent, and they take turns through a file lock rather than a daemon, because the kernel already mediates a lock file and that leaves nothing extra to deploy or restart. If a process dies while holding the lock, the next one checks the pid and breaks it. Admission is gated on memory pressure rather than on free-VRAM arithmetic, and the resident stack gets unloaded before the next one loads, because I didn't want the system relying on two models happening to fit at the same time.

Pulling it back together

After building a few of these queues by copying the same pattern each time, I realized it was only going to keep growing, so I pulled them back into a single shared engine. I did the refactor carefully: I wrote tests against the old versions first, then made sure they stayed green on the new one, so I could prove the behavior had not changed. Later I moved the whole thing onto a real database and had it keep an append-only history of every job instead of overwriting state, which means I can actually answer what happened to any job after the fact, and it keeps limping along instead of falling over when the database is unavailable.

What the system is now

The "my own Spotify" goal eventually reached the players themselves, so I forked my desktop and Android music clients to make the home-grown features show up on every screen, including my playlist folders, the looping video art the server generates for albums (which was inspired by Spotify's version), and, on the phone, the chat assistant built right into the player.

The same machinery that started with lyrics now hosts music-ML research lanes, a karaoke engine, 3D asset pipelines, and agent-driven porting campaigns. The timeline below is roughly how it grew.

  • the beginningNavidrome goes up, my own Spotify, and the missing playlists and lyrics are what everything else follows from.
  • thenThe lyrics fetcher, a cron script writing .lrc sidecars, and mood analysis starts scoring the library.
  • thenPlaylist covers need a remote GPU, so the first pull-worker queue gets built, and TTS, voice extraction, and DJ sets follow the same pattern.
  • thenEverything enters version control, and capability heartbeats arrive, where workers advertise what they can do and it gets probed live.
  • thenMore lanes get added, including stems (which feed lyric transcription), image→3D meshes, a local coding agent, a knowledge-base wiki, and a multi-agent board.
  • thenThe rename, where the "lyrics fetcher" becomes a hub, and the GPU fleet migrates from Windows to Linux, lane by lane.
  • thenVisualizer preset lab, karaoke with YIN pitch scoring, and the Kiln image→3D object lane.
  • consolidationThe copied queues get pulled back into one shared engine, carefully tested so the behavior stays the same, and later moved onto a real database that keeps a full history of every job.
  • nowThe platform grows past music into decomp research lanes, charting ML, and this portfolio.

What I took away from all this

A lot of the architecture here came straight out of the constraints. The 30-second limit on the plugin is what shaped the mood-playlist design, and the image models living on a separate machine is what shaped the pull pattern. I also learned to trust my ears over my metrics, because the numbers guided the charting models but playing the charts myself caught the things the numbers missed. And after a while working with AI coding agents, the habit I keep coming back to is to check the harness before blaming the model when an agent fails, because most of what looks like a weak model turns out to be a weak environment around it.
