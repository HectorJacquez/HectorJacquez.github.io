How a Playlist Cover Generator Became a Distributed System

One home server, a music collection that kept asking for more, and the textbook monolith-to-distributed-to-consolidation arc — except it happened in my living room.

It started with wanting my own Spotify

I left Spotify and set up Navidrome on a home server to stream my own library. Ownership felt great for about a week, and then I started missing two things: the playlists and the lyrics. Chasing those two itches built everything else on this site.

Lyrics came first. A cron script fetched synced lyrics from LRCLIB and wrote .lrc sidecars into the library so players would scroll them. Polite rate limiting, a cache for misses, a nightly timer. For the tracks nobody had ever transcribed, I eventually pointed stem separation and Whisper at my own files, and added romaji and translation for the Japanese half of my collection. The playlists itch became mood analysis: a Navidrome plugin with an audio-ML sidecar scoring every track, feeding 48 generated mood playlists — and later a chat harness that builds a playlist for whatever mood I ask for, and answers music trivia from real sources instead of a model's imagination.

And the mood playlists led to the pictures: I wanted AI-painted covers for them, and the image models lived on a different machine's GPU. That forced the first real architecture decision, and everything since has inherited it: the GPU machine pulls jobs, and the server never reaches into it. The image backend only listens on loopback and has no auth, on purpose, so the worker polls a queue, renders, and streams results back. Results come back per model, because SD-Turbo finishes in 20 seconds and FLUX takes eleven minutes, and nobody wants to wait on the slow painter to see the fast one.

The day a second machine started polling the first, the hobby became a distributed system, whether I'd admitted it yet or not.

The pattern gets copied — a lot

Once a pull-queue existed, every new want became a lane on it. Voice cloning for a daily listening brief. Stem separation, which promptly fed back into the origin lane by transcribing lyrics LRCLIB didn't have. One commit from that week I still like: "don't pay demucs to prove a track has no vocals." Looping canvas videos for album art, after probing the official source, hitting a wall, and committing the dead end as documentation so nobody retries it. Image-to-3D meshes. And a local coding agent — because after building my chat assistants on a small local model, I'd learned that models optimized for a consumer graphics card can carry real jobs, and I didn't want every task leaning on paid frontier tokens. Each lane copied the same queue-and-lease mechanics. Workers advertise what they can do through a capability heartbeat that probes everything live at beat time, a rule written after a stale venv spent four days advertising a capability it didn't have.

At the busiest stretch it was two machines and multiple AI coding agents coordinating through a shared board, with a knowledge-base wiki so that anything learned twice only had to be learned once.

One GPU, many hungry stacks

A single 12 GB consumer card serves image generation, stem separation, several local LLMs, and a coding agent. They take turns through a file lock rather than a daemon, because the kernel mediates a lock file and there is nothing to deploy, restart, or crash. If a process dies holding the lock, the next one checks the pid and breaks it. Admission is gated on memory pressure instead of free-VRAM math, and the resident stack gets put away before the next one loads. Hoping two models fit is not a memory strategy.

Consolidation: five queues become one, then become a log

By October the copies had drifted enough to hurt, so I collapsed them into a single lease engine. The migration ran diff-first: tests green on the old implementation, then green and unchanged on the new one. Two weeks later the queues went event-sourced on Postgres. Instead of a status table that overwrites itself, every state change is an append to an event log, and current state is derived from the log. That one change answered two old complaints at once: "why did this job fail last Tuesday" became answerable, and claim-to-done latency percentiles per lane came basically for free. Claims are optimistic appends arbitrated by a unique constraint, and when the database is down the hub limps instead of dying. A load test found the first real inefficiency within hours. The fix landed the next commit.

What the system is now

The "my own Spotify" goal eventually reached the players themselves: I forked my desktop and Android music clients so the home-grown features show up on every screen — my playlist folders, the looping video art the server generates for albums (yes, inspired by Spotify's version), and on the phone, the chat assistant built right into the player.

The same machinery that started with lyrics now hosts music-ML research lanes, a karaoke engine, 3D asset pipelines, and agent-driven porting campaigns. The timeline below is reconstructed from the git history — including the honest caveat that the earliest era predates version control and survives only in battle-scar comments like CONFIRMED LIVE (Aug 25 2026).

  • the beginningNavidrome goes up: my own Spotify. The missing playlists and lyrics become the roadmap.
  • thenThe lyrics fetcher: a cron script writing .lrc sidecars. Mood analysis starts scoring the library.
  • thenPlaylist covers need a remote GPU → the first pull-worker queue. TTS, voice extraction, DJ sets follow the pattern.
  • thenEverything enters version control. Capability heartbeats: workers advertise what they can do, probed live.
  • thenThe lane explosion: stems (feeding lyric transcription), image→3D meshes, a local coding agent, a knowledge-base wiki, a multi-agent board.
  • thenThe rename — the "lyrics fetcher" finally admits it's a hub. The GPU fleet migrates from Windows to Linux, lane by lane.
  • thenVisualizer preset lab, karaoke with YIN pitch scoring, the Kiln image→3D object lane.
  • consolidationFive copied queues collapse into one lease engine, migrated diff-first. Then Postgres: event-sourced queues with latency percentiles, and a CI gate over 24 suites.
  • nowThe platform outgrows music: decomp research lanes, charting ML, and this portfolio.

What I took away from all this

Constraints are where the architecture comes from. The 30-second WASM budget designed the mood-playlist plugin, and the locked-down GPU backend designed the pull pattern. I also learned to trust my ears over my metrics: the numbers guided the charting models, but playing the charts myself caught what the numbers missed. And after months of working with AI coding agents, the rule that saved me the most money: when an agent fails, check the harness before blaming the model. Most of what looks like model weakness is environment weakness.
